## Speedup Analysis

### What drives speedup

Speedup comes only from cached steps that are **skipped entirely** — no LLM call, no tool execution. The key variable is how much expensive work precedes the divergence point.

| Factor | Effect |
|---|---|
| Divergence position | Later = more steps cached = more time saved |
| Cost of cached steps | Sub-agent and task-managed steps > single file-read decisions |
| Final synthesis position | If synthesis itself is cached (no divergence), speedup is largest |
| Task length | Longer tasks have more skippable work relative to fixed overhead |

### Tests E and L: the best cache efficiency

**Test E (3.5x)**: Zero divergence — every step (including the final synthesis) served from cache. No LLM calls at all during replay.

**Test L (2.7x)**: 20 of 21 steps cache-hit. The agent used task management (	odoCreate, 	askMarkComplete) for the four review phases, reading the code file and each skill file sequentially. Complexity-limits.md (skill 4, step 20) diverged. 20 cheap steps cached, only the last skill read and synthesis ran live.

### Tests G, I: early divergence, no gain

Divergence at step 0 — the very first tool call already produces a different result. 100% of LLM calls happen live. The ~1x figure is measurement noise.

### Test F: 75% cache-hit, only 1.1x speedup

Three of four file-read steps cache-hit. The problem: the final synthesis call dominates runtime and it cannot be cached. The three cached steps are cheap intermediate "decide to read next file" calls (~4s each); the live synthesis writes the full analysis (~35-40s). Caching the cheap steps does not significantly reduce overall time.

### Test H: 1.5x speedup without caching

System prompt change is detected before any tool calls, so go-live starts from step 0 with zero cache hits. The 1.5x speedup is **not from caching** — the go-live agent used a single ileBatchRead to read all four files, while the T_fresh run made four separate ileRead calls. This is a model path-efficiency artifact, not replay caching.

### Tests K and L: multi-skill workflow shows real gains

The phased review prompt induces **naturally sequential** skill loading — the agent loads a skill when it begins that review phase, not all upfront. This produces cache-hit chains proportional to how late the changed skill appears in the load order.

| Test | Changed skill | Skills cached before divergence | Speedup |
|------|--------------|--------------------------------|---------|
| K | Naming-guide (skill 3) | Skills 1-2 + exploration steps | 3x |
| L | Complexity-limits (skill 4) | Skills 1-3 + all code reads + task steps | 2.7x |

Test K's execution took a different path: the agent used ExplorerAgent to explore the skills directory first, and ExplorerAgent detected the changed file through a **directory listing** (the file size of naming-guide.md changed when the new rule was appended). This is a realistic detection path — the replay system caught the change even without reading the file content directly.

Test L's agent was more methodical: it used task management tools (	odoCreate/	askMarkComplete) to track each review phase, reading the code file first, then each skill file as it started each phase. The divergence happened cleanly at the complexity-limits.md fileRead at step 20 of 21.

### Why Tests K and L outperform Test F despite similar structure

Test F (late file change) shows only 1.1x because the cached steps are trivially cheap (short model calls to select the next file). Tests K and L show 2.7–3x because the cached steps include: task creation and tracking calls, file reads of the code under review, and the first N-1 skill-file reads — collectively a much larger share of total runtime.

## Interpretation

- **Speedup > 1x from caching**: only when cached steps are skipped (E, J, K, L). The larger and more expensive those steps, the greater the gain.
- **Task structure matters**: Test L's methodical task-management approach (20 cache-hits) outperforms Test F's simpler file-read loop (3 cache-hits) because the task management steps themselves carry non-trivial cost that benefits from caching.
- **Agent path variability**: Tests K and L used the same prompt but took different execution paths (ExplorerAgent vs. task-managed sequential reads). Both correctly detected the changed skill. This is expected — agent behavior is not deterministic — but it means replay efficiency varies across runs.
- **File size as a divergence signal**: Test K shows the directory listing acting as an indirect divergence detector. When a skill file's content grows, its byte size changes, the listDirectory result differs, and divergence is caught without reading the file itself.
- **Early divergence = no gain** (G, I): if the changed artifact is encountered on the first tool call, replay is equivalent to a fresh run.
- **Detection channels**: system prompt hash (H — triggers before any tool call) and tool result hash (all others — triggers at the first changed tool call, direct or indirect).
