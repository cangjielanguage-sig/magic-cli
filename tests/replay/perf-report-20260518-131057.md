## Speedup Analysis

### Why Tests G, H, I show no meaningful speedup

All three diverge before any step is cached, so the replay is functionally equivalent to a fresh run. The ~1x figures are measurement noise.

**Tests G and I** diverge at step 0 — the very first tool call (skill file read / shell command) already returns a different result. There is nothing before step 0 to cache, so 100% of LLM calls happen live.

**Test H** is more subtle. The system prompt hash changed before any tool calls are checked, so go-live is triggered from step 0 — the same outcome. The reported 1.5x speedup is **not genuine caching**: the go-live agent happened to batch all four file reads into a single `fileBatchRead` call, while the separate T_fresh run used multiple individual `fileRead` calls. This is a path-efficiency artifact of the model's choices in that particular run, not a property of system-prompt-change replay.

### Why Test F (late-stage change) only achieves 1.1x

Three of four file-read steps cache-hit, yet the speedup is minimal. The reason is that **the final synthesis call dominates the total runtime** and it cannot be cached:

| Phase | Time (approx) |
|---|---|
| 3 × "decide to read next file" LLM calls | ~4–5s each |
| 1 × diverged file read + live LLM decision | ~5s |
| Final synthesis (write full analysis of all 4 files) | ~35–40s |

Caching the three intermediate file-selection decisions saves at most ~12–15s, but the synthesis step — which must run live regardless — accounts for more than half the total time. The task is also too small (4 steps, ~60s fresh) for the fixed overheads to amortize well.

### Why Tests E and J achieve meaningful speedup

**Test E (3.5x)**: Zero divergence — every step (including the final synthesis) is served from cache. No LLM calls at all during replay. The only cost is trace loading and hash comparison.

**Test J (2x)**: 7 of 8 steps are cached, including an entire `ExplorerAgent` sub-agent invocation. A sub-agent call is expensive because it runs its own multi-step LLM loop internally. Skipping one sub-agent step saves far more time than skipping a simple `fileRead` decision call.

### What drives good speedup

| Factor | Effect |
|---|---|
| Divergence position | Later = more steps cached = more time saved |
| Cost of cached steps | Sub-agent calls >> file reads — cache them for big wins |
| Final synthesis position | If synthesis itself is cached (no divergence), speedup is largest |
| Task length | Longer tasks have more skippable work relative to fixed overheads |

## Interpretation

- **Speedup > 1x from caching**: only when cached steps are skipped (Tests E, J). The cached steps must themselves be expensive — sub-agent calls (J) or a synthesis step (E) — to produce large gains.
- **Speedup ≈ 1x**: divergence happened at step 0, so 100% of work ran live (Tests G, I). Also Test F despite 75% cache-hit rate, because the dominant synthesis step ran live.
- **Apparent speedup without caching**: Test H's 1.5x reflects the model choosing a more efficient path during go-live (one `fileBatchRead` vs four separate reads), not replay caching.
- **Task size matters**: short tasks with a dominant final synthesis step (F) benefit little even with late divergence. Long tasks with expensive cached steps (J) benefit most.
- **Detection channels**: system prompt hash (Test H — triggers before any tool call) and tool result hash (all others — triggers at the first changed tool call).
